# 项目规则、可选能力与偏好

这三个位置各解决一个具体问题，不要求每次任务都走一遍。

| 内容 | 放在哪里 |
| --- | --- |
| 本项目的命令、目录、领域约束和维护要求 | 项目已有的 `AGENTS.md` 等宿主实际加载的说明。 |
| 用户任务、业务规则、流程、交互、视觉和可观察验收条件 | 项目产品设计文档；`design` 在相关设计工作中按需建立和维护。 |
| 背景约束、模块职责、技术栈、DB 与中间件、数据状态归属和取舍 | 项目架构文档；`eng` 在相关工程工作中按需建立和维护。 |
| 特定任务需要的设计资料、验证方法和外部 CLI 用法 | 对应的可选 Skill。 |
| 所有开发任务的工程行为与品味 | `eng` 入口的共同原则；配套资料只读取当前取舍需要的内容。 |
| 仓库内经验与确认偏好 | 已指定的仓库经验日志，否则使用根目录 `.agent-learning.md`；全局记忆必须由用户明确要求。 |

`reflect` 在日常纠正、失败和有证据的改进后复盘，将可复用经验留在仓库。经验、待验证假设和用户确认偏好分开记录；不将学习日志自动升级为团队规则。写入遵从宿主规则，宿主限制自动持久化时只在对话中总结；已有授权无需重复询问。`grill-me` 用于用户请求的决策追问，不是所有任务的必经流程。

移除通用 Skill 时，不把其完整流程搬进始终加载的规则文件。仅保留能影响该项目工作结果的约定。当前目录和迁移方式见 [README](../README.md)。

## 项目文档与导航

产品设计记录回答用户应获得什么结果，架构记录回答系统通过什么机制兑现它；运行与操作证据用于检查二者是否一致。`verify` 可以据此建立检查预期，但文档、代码和现有测试之间的冲突需要查明，不能用实现现状循环证明预期正确。

优先复用项目已有资料。发生实质性产品行为或架构变化时，只建立或更新当前任务需要的那份最小记录；没有合适落点时，分别可用 `docs/product.md`、`docs/architecture.md`。普通小修复无需为了流程新建两份文档。产品记录区分已确认决定、建议和假设；架构记录区分当前实现和计划方案。

项目 `AGENTS.md` 可在项目规则和当前授权允许时，登记实际文档路径、用途与相关变化后的同步约定。例如某项目可以注明“产品行为见 `docs/product.md`，系统机制见 `docs/architecture.md`”；这是路径示例，不是通用固定目录或修改项目规则的授权。不要复制文档正文，也不要因维护文档自动调用多个 Skill 或增加审批。

## 偏好的作用域与更新

- 个人偏好放在宿主允许的个人位置；只有已授权的团队或项目约定才进入共享仓库。打开一个项目不构成写入团队规则的授权。
- 用户明确替换同作用域偏好时更新原条目，避免新旧规则同时生效。局部例外保留边界，例如“旧包使用 npm，其余包仍用 pnpm”。
- 用户明确撤销时只撤销对应条目，不推导相反偏好。宿主只允许更新说明时，使用该机制而不直接改写记忆文件。
- “这次标题改成红色”属于当前任务要求，不自动变成“所有标题都用红色”。明确记录请求与普通纠正的区别见 [reflect 示例](../reflect/SKILL.md#scope-conflicts-and-retraction)。

## 参考资料与项目规则的区别

`eng` 的工程例证和 `verify` 的场景用于帮助选择方法，不要求每个项目实施全部模式或执行全部检查。`design` 保留交互、视觉、动效和直接影响使用的无障碍约束；工程原则由 `eng` 负责，具体框架实现按需查阅专业资料。设计建议服从产品 brief、已有设计系统和平台习惯。不要把这些可选参考整体复制到始终加载的 `AGENTS.md`，也不要把其示例当作已经执行的验收证据。
