# 验证

依据已确认标准和真实证据检查业务规则、用户旅程或最终验收，默认用中文直接回答被问的问题。业务诊断和规则保护**不使用**最终验收标记（`accepted` / `rejected`）。

## 范围与连续工作

- **诊断与最终验收保持只读**：不修改被审查的源码或测试。在已有授权与环境允许时，可运行现有检查、操作隔离测试数据并清理临时产物；产生真实外部效果或触碰生产环境须有明确授权。
- **保护指定业务规则**：以已确认规则（而非现有代码实现）为预期，按现有测试模式补充最小且能检出对应失败的检查。未同时获准修复产品代码时保持实现不变，将偏差作为发现报告，不降低预期迎合现状。
- **衔接后续授权工作**：检查结束后，对已获授权的修复或后续任务直接推进，不要求额外确认或切换流程；缺乏执行工具时如实说明工具不可用，不声称已完成修改或检查。无关旅程与可选缺口不自动衍生新任务。

## 检查步骤

1. **确立预期来源**：以当前已确认需求、产品设计（如 `docs/product.md`）或用户给定规则为准，结合架构资料定位实现机制；代码和旧测试只反映现状，不能反推预期正确。无产品或架构文档时直接按用户给定的明确规则开展检查，**不把补建文档设为前置条件**；冲突无法从现有证据判定且会影响结论时再询问。
2. **聚焦高风险边界**：沿改动触及的入口、状态转换、持久化与外部副作用，优先挑选后果严重且证据薄弱的场景（正常、失败、重复、乱序、取消、切换或恢复），写清预期效果与观察点，不机械穷举。
3. **验证真实约束机制**：用成本最低且包含实际约束机制的方式检查（纯逻辑可用单测；唯一性、原子性、幂等、跨账号隔离等须覆盖真实存储或沙箱机制，模拟测试与界面成功提示不能替代）。版本与条件未变时复用有效证据；选择复现方式时按需查阅 `references/scenarios.md` 中匹配的场景。
4. **按实际证据报告**：区分已证实缺陷与待验证假设，没有发现缺陷也如实说明。需要记录具体问题时可按需包含：**触发条件**、**预期及来源**、**实际行为与影响**、**证据位置**、**状态（已证实 / 假设及所缺证据）**，不必套用固定模板。

## 最终验收

仅在用户要求给出最终验收结论时，使用以下三项标记之一：

- `accepted`：所有约定标准与必需检查均有充分证据支持。
- `accepted with risk`：无未满足的阻塞标准或缺失的必需检查，但存在已明确列出的非阻塞风险（如已约定不阻塞的旧环境兼容项）。
- `rejected`：某项标准不满足、存在阻塞回归，或**缺少必需检查证据**（包括必需检查出现间歇失败、仅靠重跑通过而未查明原因）。明确说明是“已证实不符”还是“必需证据不足”。

判定规则：

- **逐条核对标准**：给出结论前将每条约定标准对应到实际证据或缺口，不凭整体印象放行，也不把相邻可选场景临时升级为阻塞门槛。
- **处理不可观察标准**：遇到“体验流畅”“性能良好”等模糊标准，先按已确认需求落成可观察条件；无法落成且无法向用户澄清时，标为**无法判定**并按证据缺口处理，不计为通过，也不自行发明阈值。
- **区分自查、独立审查与发布权**：同一实现者自查不能称为独立审查；获准开展独立审查时，先将原始标准、版本与原始证据交给未参与实现者判断。技术验收不授予合并或发布权限。
