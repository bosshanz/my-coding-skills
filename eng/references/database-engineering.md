# 数据库工程

任务涉及数据建模、约束索引、事务并发、数据删除/保留、生产库访问或模式迁移回填时阅读。仅调用既有仓储接口且不改模型、查询、事务或删除语义时无需加载。

## 数据模型与约束

- **事实源与规范化**：从读写路径、不变量与预期数据量出发，为每份数据明确唯一事实源（缓存、搜索索引、读模型须可从事实源重建）；在实测访问瓶颈支持前保持规范化，优先复用现有数据库与迁移工具。
- **数据库层强制不变量**：用主键、外键、唯一约束（防重与幂等）、检查约束和 `NOT NULL` 兜底，不仅靠应用层先查后写。对外避免直接暴露易被枚举的自增 ID；可空列须明确 `NULL` 的业务含义（未知 / 不适用 / 待回填）。

## 破坏性数据操作

不要给所有表一律加 `deleted_at`，按数据性质选择生命周期（ORM 的 `destroy`、`deleteMany`、`onDelete: Cascade` 等同于物理 `DELETE`）：

| 数据类型 | 生命周期做法 |
| --- | --- |
| 订单、账本、账号、权限、审计等核心领域记录 | 明确状态转换（`cancel`、`void`、`revoke`、`expire`），账本与资金流水**仅可追加**（用冲正新行更正，不改删原行）。 |
| 删除后仍需查询“曾存在但已移除”的身份记录 | 墓碑记录，并明确唯一索引、默认查询与外键对非活动行的语义。 |
| 临时数据、可重建派生数据，或已触发保留/擦除策略的数据 | 允许物理 `DELETE`，但必须限定在明确主键集合或固定批次内，且有明确责任方与恢复方案。 |

硬边界：不在应用代码中放 `TRUNCATE` / `DROP TABLE` / `DROP DATABASE`；不执行无 `WHERE` 或无界范围的 `UPDATE` / `DELETE`；不把级联物理删除作为领域聚合默认策略；不靠置空业务字段抹除历史记录。

## 生产数据访问

未知库、共享库、含生产数据的预发库和生产库，**未获针对目标与操作的明确批准前一律只读**：

- 默认只用 `SELECT` 或 `EXPLAIN`；生产库不默认执行 `EXPLAIN ANALYZE`（会真实执行并可能加锁）。
- 获批执行线上写操作前，先估算影响行数并准备回滚/修复方案，不用应用凭据“顺手修一行”。
- **严禁对生产 `DATABASE_URL` 直接执行迁移、播种或清空**（普通写入授权不解除此禁令；编写迁移脚本和操作可丢弃的本地隔离测试库不受限）。

## 查询、索引与事务并发

- **查询与索引**：所有列表、导出和后台扫描必须有界（游标分页或定长批次）。按“等值条件 → 范围条件 → 排序”结合优化器行为设计复合索引，避免重复前缀索引、N+1、隐式类型转换、索引列套函数或前置通配符；大表与热点路径用非生产真实规模数据跑 `EXPLAIN`。
- **短事务与锁**：事务保持短小有界，**严禁持有数据库锁调用 HTTP、邮件或外部队列**。普通并发编辑用乐观锁返回冲突；悲观锁仅限短临界区并固定加锁顺序与超时；并发正确性依赖隔离级别时显式注明假设。
- **稀缺余额原子更新**：资金、库存、名额、优惠券等严禁“先读后改再写”，必须使用单条条件更新（如 `UPDATE ... SET bal = bal - :n WHERE id = :id AND bal >= :n`），影响行数为 0 视为业务失败。

## 迁移与回填安全

繁忙生产表优先采用**扩展—迁移—收缩**五步法，避免阻塞式锁表重写：

1. 添加兼容新结构（不在已有数据的表上直接加无默认值的 `NOT NULL`，不原地改繁忙列类型/枚举，未清理重复行前不建唯一索引）。
2. 部署兼容读写代码，明确新旧并存期间的权威字段。
3. 脱离结构变更事务，分有界、限速、可暂停恢复的批次回填历史数据，带版本条件防止覆盖并发新写入。
4. 校验一致性后切换读取。
5. 回滚窗口关闭后再移除旧结构（有些数据迁移只能向前修复，须在上线前如实说明）。

## 示例：重命名已有数据的列与在线建索引

- **列重命名（`display_name` → `public_name`）**：直接 `RENAME COLUMN` 会导致滚动发布中的旧实例报错。应新增可空 `public_name` → 部署双写/同步 → 有界批次回填（不覆盖更新写入）→ 对账后切读 → 窗口结束后删旧列。在同版本隔离库模拟新旧读写并存、回填中并发更新与中断恢复，并用代表性数据量评估锁与耗时。
- **PostgreSQL 专用在线索引**：大型线上 PG 表使用 `CREATE INDEX CONCURRENTLY` 减少写阻塞（不能在事务块内运行，注意迁移工具的自动事务包装；构建失败可能残留 `INVALID` 索引，恢复时须检查有效性而非仅看同名索引存在）。详见目标版本 [PostgreSQL CREATE INDEX 文档](https://www.postgresql.org/docs/current/sql-createindex.html)。示例结构借鉴 [Supabase Postgres 最佳实践](https://github.com/supabase/agent-skills/tree/main/skills/supabase-postgres-best-practices)。

## 容量与故障排查

- **容量意识**：非微小改动前估算行数增长、读写 QPS、热点键、索引膨胀与备份恢复时长；调高应用并发前先核对连接池上限（数据库饱和常先表现为应用端排队延迟）。使用只读副本时明确哪些路径必须走主库。
- **排障切入点**：慢查询查 SQL/基数/执行计划；死锁查语句锁顺序与事务时长；数据不一致查事实源、回填与复制延迟；连接耗尽区分慢查询、长事务、连接池配置与泄漏；迁移事故立即限速或停止，保留现场并核实回滚可行性。
- **可选决策提纲**（仅在项目或用户要求正式数据库方案文档时按需选用）：`访问模式 | 不变量 | 模型与索引 | 事务与隔离 | 保留与删除 | 迁移与回填 | 容量与回滚 | 验证`。
