# 代码审查

用户要求审查改动、PR 或一段代码时使用。审查默认只读：报告发现，不修改被审查的代码，除非用户同时要求修复。实现过程中的自查不需要单独的审查报告。

## 先弄清审查对象

- 确定范围和基线：哪些提交或文件、相对哪个版本、改动声称解决什么问题。范围不明且无法从上下文或版本历史查清时再询问。
- 阅读完整差异及其触及的调用方、契约和数据，不只看差异行本身。判断行为是否兑现改动声称的目的，而不只是代码是否自洽。
- 风格、命名和结构以项目规则和周边代码为准，不以个人偏好为准。

## 按后果分配注意力

按后果排序，不按文件顺序或发现的先后。下面是常见的关注方向，实际轻重取决于这次改动的风险：

- **正确性与数据：** 逻辑错误、状态与并发、失败路径、数据丢失或损坏、迁移与回滚。
- **契约与兼容：** 公开接口、协议、持久化格式，以及已有使用者依赖的行为。
- **权限与信任边界：** 授权是否落在实际动作上，外部输入如何处理，凭据与私密数据是否外泄。
- **验证：** 测试是否覆盖实际执行约束的机制，是否为了通过而削弱预期。
- **可维护性：** 不必要的实体、含混的命名与归属、隐藏的副作用。

格式和纯风格问题交给项目已有的格式化与 lint 工具；确需指出时合并为一条，不逐行罗列，也不与缺陷并列。不为显得全面而凑数：没有发现重要问题时直接说明，并指出审查没有覆盖的部分。

## 让每条发现可以核对

- 指明位置（文件与行）、触发条件、预期与实际后果。能用项目已有检查或最小复现确认时先确认；只读审查可以运行不改变代码的检查。
- 区分已证实的缺陷、有依据的怀疑和需要作者回答的问题。未验证的怀疑写明还缺什么证据，不把推测写成结论。
- 说明严重程度及理由，把应当阻塞合并的问题与可以后续处理的建议分开。改法只在能澄清问题时给出，不替作者重写无关部分。
- 审查自己参与实现的改动时如实说明，不称为独立审查。

## 边界

审查结论不授权合并、发布或修改代码。业务规则检查、用户旅程诊断和带验收标记的最终结论属于用户明确要求时才使用的 `verify`；普通代码审查不需要验收标记。
