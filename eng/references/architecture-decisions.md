# 架构决策与模块边界

用于判断模块是否值得拆分、接口边界画在哪里，以及如何开展编码前的技术调研。跨进程演化、缓存队列与线上运维见 `software-architecture.md`。

## 何时新增或调整模块边界

新增模块、接口、依赖或配置必须解决当前真实问题，且收益大于理解、维护和运行成本：

- **反例（过度设计）**：单一实现且无替换或隔离需求，却提前搭建注册表、抽象工厂和插件协议，调用方仍需理解底层细节。
- **合理边界（单调用方也成立）**：能隔离外部网络/存储副作用、集中必须同步演进的业务规则，或拆开传输与解析以便离线重放测试。调用方数量不是拆分门槛。
- **重判信号**：同一规则散落多处导致改一漏一，或调用方被迫反复处理底层细节时，应收敛边界；反过来，若某层只剩纯透传、不断靠布尔/例外参数打补丁，或把变化原因不同的代码硬绑在一起，应拆开或内联移除。

## 代码库设计术语

讨论重构或模块划分时，用以下概念衡量结构质量：

- **深模块 vs 浅模块**：好模块用窄而清晰的**接口**（类型、不变量、调用顺序、错误与性能预期）隐藏复杂的内部实现（**深度**高）；若删掉某模块后复杂性随之消失，说明它只是无意义的纯转发层（**删除检验**）。
- **局部性与变化接缝**：把因同一原因变化的逻辑与状态放在一起（**局部性**），使改动与排错集中在单处；仅在确有替换或测试隔离需求的位置留出**变化接缝**与**适配器**，不按目录名机械分层。

删除检验是设计启发；若需实测某个可选组件或规则的真实贡献，按需使用 `ablation.md`。

## 软件工程调研

对库行为、协议细节、数据模型或中间件语义不确定时，先查证再落笔：

- 优先核对与项目锁定版本一致的一手来源：官方文档、源码、RFC 或最小本地验证。
- 只记录影响当前决策的结论：选了什么、排除了什么、受哪些版本或环境前提约束。

## 示例：发布状态由单一模块负责

- **场景**：界面、HTTP 处理器和后台工作进程都在表达同一次发布。
- **反例**：HTTP 入队即写 `published = true`，工作进程单独记投递结果，前端凭 200 响应直接报成功——一旦后台失败，三处对“是否已发布”各执一词。
- **做法**：在现有合适的领域模块中统一定义状态机（如 `queued -> running -> succeeded | failed`，含部分成功时的逐项状态）与操作版本令牌。HTTP 只确认入队；工作进程执行带版本约束的状态转换（拒绝重试或取消后的过期回调）；前端直接展示该权威状态，无需为此新建独立微服务。
- **验证**：注入工作进程失败、延迟重放及“新尝试启动后收到旧尝试完成回调”，核对持久化状态与各端展示一致；仅测前端渲染无法证明状态机约束生效。
