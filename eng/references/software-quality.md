# 软件质量

## 范围

在已有结构内判断代码、契约、状态、副作用、资源、测试和交付是否可靠。只读当前改动涉及的约束；微小机械修改不要求展开完整质量检查。结构与依赖取舍见 `software-architecture.md`，存储语义见 `database-engineering.md`。

成功意味着约定效果实际发生，失败与未知也必须如实表达。以下原则适用于库、工具、应用和服务；后文协议、租户和数据库例子只在对应机制存在时使用。

## 可读性与局部理解

- 命名表达领域对象、动作和单位。同一概念保持一致用词，不用 `data`、`manager` 等笼统名称隐藏多种职责；短小局部变量可遵循清楚的语言惯例，不机械要求长名称。
- 控制流、副作用和依赖应容易追踪。避免隐式全局状态、出人意料的运算符行为或依靠调用者记忆的初始化顺序。
- 注释记录代码本身无法说明的原因、约束、外部约定和重要取舍，随行为一起更新。不要用注释复述语句或为难懂结构辩护。
- 采用项目中熟悉、直接的表达。函数长度、文件数和嵌套层数是判断线索，不是固定配额；不为了表面简短而压缩可读性，也不拆出没有独立含义的小层。

## 契约与数据表达

- 明确输入、输出、允许状态、错误和副作用。类型、构造方式或边界校验应尽量排除非法组合，内部代码不必反复猜测输入含义。
- 多个布尔参数或可选字段组合难以理解时，用有意义的命名、枚举或数据结构表达；简单且含义清楚的布尔值无需强行包装。
- 时间明确时区、时间点或时长，数值明确单位、范围、精度和舍入，文本或文件边界明确编码及必要的规范化规则。不能依靠不同调用方各自猜测。
- 区分缺失、空值、空集合、未加载和失败；默认值只有具有明确语义时才使用。外部无效输入应在可信边界被拒绝或按约定转换。
- 对解析、序列化和格式转换保留信息与精度；有损转换须符合约定，不能无声改变身份、金额或状态。

## 状态与并发

- 同一事实有明确的状态负责人，派生值和副本不能各自定义成功。状态转换在实际写入或更新处执行约束。
- 异步结果只更新仍属于它的操作或版本，旧搜索、加载或保存的完成不能覆盖更新输入。先检查再执行不能自动抵御并发或异步交错。
- 重复操作可能发生时，明确哪些效果可重复，哪些需要幂等或去重；失败后重试不能造成重复外部效果。
- 取消、离开、销毁和重启各自意味着什么，应与产品约定一致：停止未来工作、保存已完成部分、恢复草稿，或仅停止展示。不能仅改变提示就声称任务已停止。
- 冲突是需要处理的结果，不是成功。选择版本检查、串行化、锁或原子更新，应依据实际共享状态和运行机制，不规定所有软件使用同一种并发模型。

## 副作用、错误与恢复

- 可观察结果与实际效果一致。承诺保存时等待相应持久化确认；仅排队时报告已排队，不能声称已完成。部分完成需有明确逐项结果或已约定的原子回滚。
- 不用空捕获、无条件返回空集合或默认成功吞掉失败。未知、缺失、拒绝、超时和取消只有语义确实相同时才可合并。
- 回退必须有业务含义，例如显示标明时效的缓存；不能把读失败解释为数据不存在，并据此覆盖有效数据。保留原始原因和必要上下文，使问题可诊断。
- 错误通过调用方能够理解的契约传播，不暴露密钥、私密数据或不必要的内部细节。错误码被使用方依赖时，改变含义也属于兼容性变更。
- 重试只针对可能恢复且重复执行安全的失败，有次数或时间预算，并尊重取消。不能靠无限重试隐藏故障。
- 多个副作用无法一次完成时，明确已发生什么、什么仍未知，以及哪种恢复安全；恢复不能丢弃无关用户工作。

## 资源与信任边界

- 文件、订阅、计时器、线程、连接和内存有明确释放或移交责任。失败、提前返回和取消也遵循同一生命周期约定。
- 对可能失控的输入、结果、批次、并发、缓冲和重试设界限。外部调用有适当超时；运行时支持时传播截止时间和取消，避免调用方离开后仍启动昂贵工作。
- 外部数据、路径和对象标识不自动可信。按实际边界处理路径越界、注入、权限和资源消耗；不将输入直接拼入 SQL、shell 或脚本，值采用绑定或对应环境的安全传递方式。
- 权限在实际动作和资源边界落实。界面隐藏、内部入口或功能开关不等于授权；需要认证的软件在可信入口认证，内部模块复用可信上下文。
- 日志保留必要的动作、结果、时间和关联信息，不记录凭据或私密原始载荷。诊断信息应能区分正常业务结果与运行故障，避免无用的高频日志。

## 测试约束行为，允许实现演进

- 预期来自需求、公开契约和不变量，不复制实现的计算过程作为唯一判定。修复尽量先证明原始症状能被检出，再比较修复结果。
- 在包含实际约束机制的最低层验证。纯逻辑可用单元测试；持久化唯一性、原子写入和查询隔离需要相关存储语义，移除机制的模拟不能证明其保证。
- 不把私有方法调用顺序、内部字段或无意义的大快照当作稳定契约。只有顺序本身有业务含义时才约束顺序；合理重构应保留行为测试，契约变化则需要对应更新。
- 时间、随机性和外部依赖影响结果时采用可控制输入或隔离替身。异步检查等待可观察条件并设超时，不用固定长等待碰运气；也不能把需要验证的真实竞争或存储机制全部模拟掉。
- 覆盖会改变结果含义的边界和失败路径，不以覆盖率或测试数量代替判断。修复脆弱测试时纠正同步或契约，不删除断言、放宽预期或只反复重跑直到通过。
- 检查规模匹配实际风险，复用仍适用的证据。未执行的必需检查仍是缺口，静态通过不证明运行时行为。

## 对实际交付物负责

- 构建输入、工具链、依赖版本和必要配置应能从仓库及项目约定中确定；不依赖未声明的全局工具、本机绝对路径或偶然缓存。遵循现有锁文件和构建方式，不为可复现性另造平台。
- 配置有明确来源、优先级和有效范围。缺少必需项时在使用前清楚失败；真正可选项可以有明确默认值，不用默认配置掩盖部署错误。
- 涉及构建、打包、依赖、资源路径或交付方式的改动，应检查实际生成的包、程序或部署产物。开发服务器启动、源码测试或构建退出成功，各自不能代替产物可用性。
- 根据本次改动，在适当的干净或隔离环境验证受影响的安装、启动、导入、资源读取或关键行为；只验证必要路径，不要求每次局部改动重跑所有发布矩阵。
- 报告源码版本、使用的构建方式、实际验证的产物及未覆盖环境，详细程度按交付规模调整。不要把本机结果外推为所有平台或生产可用。
- 公共接口、文件格式、保存数据和使用者依赖的行为保持约定兼容。升级、回滚和卸载涉及数据时，保留必要恢复路径；验证产物不授予发布、安装到全局或修改生产的权限。

## 条件性例子

下面是通用原则在具体机制中的应用，不要求所有软件引入 HTTP、数据库、队列、应用服务或数据仓储层。

### HTTP、授权与租户

- 使用 HTTP 时，`GET`、`HEAD` 等安全方法不隐藏写入，输入按协议模式验证，拒绝客户端无权设置的角色、价格、租户或状态字段。筛选和排序标识符使用允许列表。
- 针对动作与资源授权；从认证主体推导租户和所有者。客户端提供的 `org_id`、`user_id`、`tenant_id` 和对象 ID 是待验证声明，不是权限。
- 缺失认证、认证失败或租户归属不明确时默认拒绝。除非产品允许，拒绝不得泄露其他主体资源是否存在。管理工具和身份模拟也有明确、可审计的权限范围。
- 将验证失败、未认证、禁止访问、未找到、冲突、限流和依赖失败映射到稳定结果，不向外泄露堆栈、SQL、内部主机名或配置。
- 服务指标区分业务结果与运行故障，标签保持低基数，不使用用户 ID 或包含 ID 的原始路径；按需要追踪出站调用，不在高频循环每步都增加追踪片段。

### 数据库写入与后台任务

- 对稀缺余额使用带条件更新，零行更新视为业务失败；用户编辑的版本条件不匹配视为冲突。具体约束、事务和迁移采用 `database-engineering.md`。
- 创建、支付和触发任务等可重试效果需要幂等键或天然唯一约束。数据库提交与事件发布不能分离时，使用项目的 outbox 或等价事务性记录；不持有行锁调用 HTTP、SMTP 或队列代理。
- 至少一次投递的任务应能安全重复执行；不可处理消息经有限重试进入可诊断的终止路径，不能无限循环。
- Webhook 按提供商协议验证签名或真实性，必要时检查时间戳和重放，再执行幂等写入。
- 已有应用与数据仓储分层时，明确谁负责资源授权、事务和存取；不为满足层次名称添加纯转发模块，也不在数据仓储重复解析用户凭据。

### 服务进程运行

- 存活表示进程应继续运行，就绪表示它能提供承诺的服务。关键数据存储不可用时不能报告就绪；可选依赖失败按已定义降级处理。
- 关闭时停止接收新工作，排空进行中的工作或交还可恢复的任务，再释放资源退出。
- 不把生产数据模型迁移作为接收流量的意外副作用；只有项目已明确且审查的机制才可采用。

### 重试库存预留

- **适用情形：** 客户端或工作进程可能在超时后重复预留。
- **反例：** 读取 `requests[key]`，不存在则扣库存，然后保存结果。两个调用方都可能通过读取检查；扣减与结果写入之间崩溃会留下未记录效果。
- **更好的结构：** 从认证上下文取得租户，验证数量为正，将键绑定到操作和规范化载荷指纹。在一个数据库事务内，占用唯一的 `(tenant, operation, key)`，执行带条件的库存更新并保存结果。遇到重复时，按数据库冲突语义读取已提交结果；同键不同载荷应拒绝。明确进行中操作是等待还是返回可重试状态。事务回滚不得留下成功占用记录。
- **验证：** 向实际执行约束的数据库发起并发相同请求，检查只有一次预留、一次库存扣减和一致结果。丢弃已提交事务的响应后再重试。用同一键和不同数量请求，预期冲突。在提交前注入失败，检查没有部分效果残留。

这个本地事务不能让外部支付或消息也具有原子性。远程效果需要提供商的幂等约定与对账，或项目的持久化 outbox；不要持有数据库锁调用提供商。

### 跨租户文档访问

- **适用情形：** 已认证用户提供租户对象的 ID。
- **反例：** `findById(input.id)` 后直接更新，只在列表页检查租户。其他租户的 ID 可绕过列表页。
- **更好的结构：** 对请求动作授权，将读写限定在已认证租户内。例如更新条件同时绑定 `id` 和可信 `tenant_id`。请求中的租户选择器必须先依据操作者允许的成员关系检查。缓存键、导出和后台任务须保留同一范围。
- **验证：** 创建租户 A 和 B；用 A 的凭据和 B 的对象 ID 检查相关读写路径。预期产品规定的不泄露信息的拒绝，并确认 B 的行未变化。包含同租户成功操作，防止全部拒绝的实现通过。使用行级安全（RLS）约束时，测试应采用真实应用角色，而不是所有者或绕过角色。
