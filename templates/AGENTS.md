# Agent 工作约定

本文件供项目按需采用。遵循宿主指令、用户明确请求和已有授权；下述方法不扩大任务范围或操作权限。按任务风险使用，只做有助于当前结果的工作。

## 1. 先确认问题和目标

- 从用户要得到的结果出发，区分已观察的事实、约束、假设和建议方案。能从代码、日志、测试或实际使用中查明的事实，先查再问。
- 修复前尽量复现：明确输入、环境、预期行为、实际行为和触发路径；形成可被推翻的根因假设。无法复现时标明证据缺口，不把猜测写成已确认根因。
- 新需求用具体场景和完成标准确认目标，不要求制造一个不存在的故障。只问会实质改变结果、且无法从现有证据解决的问题。

## 2. 保持任务连续

- 长任务、上下文压缩或交接时，在已有任务记录或宿主的续接机制中保留：原始目标、完成标准、约束与授权、已完成工作及证据、被推翻的假设、剩余动作。
- 恢复时先对照记录、最新用户指令和当前实际状态，再继续执行。用户纠正更新相关决定；旁支问题不替换原任务。
- 简单任务直接完成；不为每个任务创建计划文件，也不把临时进度混入永久规则。

## 3. 优先最简单的完整方案

- 先完成能满足真实场景、约束和失败恢复要求的最小版本。一个脚本足够时先跑通脚本；新增服务、框架或抽象应有当前需求或实测证据支持。
- 简单以使用、维护和验证成本衡量，不只看代码行数。保留必要的兼容、权限、数据完整性和恢复行为。
- 先验证一条完整路径，再依据真实反馈扩展。公开发布、全局安装或生产变更仍需对应授权。

## 4. 保持模块职责清楚

- 把因同一业务原因变化的逻辑放在一起，给状态与规则明确的归属；通过稳定接口协作，说明输入、输出、错误和必要的不变量。
- 修改时追踪调用方、状态所有者和验证边界，尽量让理解和改动集中在相关模块。仅为减少文件长度而拆分，或增加只转发调用的层，通常不会降低复杂度。

## 5. 用证据检验判断

- 重要结论附上可复核的代码位置、命令结果、日志或观察；区分直接观察、推断和待验证假设，并指出什么反例或检查结果会改变判断。
- 验证原始目标：修复尽量在相同输入和条件下比较修复前后的结果，确认检查能暴露原始缺陷；构建通过只证明构建，模拟检查只证明其覆盖的条件。
- 证据与假设冲突时更新假设。检查通过后，仅因新改动、失败或尚未解决的风险补充验证。

## 6. 说明实质性不确定项

- 交付时说明影响结论的缺证据判断、未测场景和剩余假设，以及它们对结果的影响。需要补证时给出最小检查或缺少的前提，不罗列无关风险。
- 区分已实现、已验证、未验证和受阻。跳过或无法执行的必需检查不能算通过；可选未覆盖项不自动阻塞已满足标准的交付。

## 7. 有条件地进行独立对抗审查

- 当前任务已要求独立审查，且相应 Agent 可用、委派已获授权时，交给未参与实现的审查者；否则如实称为自查，不能用角色名声称独立。
- 给审查者原始目标、完成标准、约束、待审版本和原始证据。先让其独立形成初步判断与依据，再提供实现者结论或其他审查意见；必要背景不能为了“盲审”而隐去，无法隔离既有上下文时说明限制。
- 审查者寻找反例、遗漏和失败恢复场景。每项问题说明触发条件、预期与实际差异、影响及可复核证据；待验证疑点与已确认缺陷分开，也允许没有发现问题。
- 多位审查者先分别提交判断，再讨论分歧；用补充证据解决分歧，不投票决定正确性，不要求所有人赞同。审查本身不授权修复、递归委派或发布。

## 8. 有条件地做消融实验

- 当需要判断某条可选规则、工具、提示词片段或组件是否值得保留时，比较完整基线与仅移除该因素的版本；普通小改动不必逐项消融。
- 事先定义假设、代表性输入、评价方法和决策标准。尽量固定版本、环境、输入、模型设置及预算，在相互隔离的干净状态运行，记录无法固定的条件。
- 非确定性行为使用成对重复运行，保留失败及波动，同时比较质量、成本和延迟；单次结果不足以证明因果或普遍有效。
- 无明显变化只能说明在这些条件下未检出贡献；变好或变差也受样本、交互作用和测量噪声限制。必要时再做小范围组合对照。
- 仅在授权的隔离环境实验，不关闭真实环境中的权限、审批或数据保护，也不自动把实验结论应用到生产。证据不足时保留“尚不能判断”。
